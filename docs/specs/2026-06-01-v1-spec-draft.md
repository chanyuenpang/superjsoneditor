# Super JSON Editor 第一版规格草案

## 一、产品目标

第一版不是要做一个只服务单项目的网页工具，而是要做一个可以被多个项目复用的通用 JSON 编辑器基础能力。

第一版完成后，应当能够：

- 在网页项目中被引用
- 编辑任意 JSON 文档
- 支持嵌套对象和数组
- 支持通过多级次页方式深入编辑任意深度结构
- 为外部宿主项目提供接入入口

## 二、核心能力

### 1. 基础 JSON 编辑

支持以下数据类型：

- `string`
- `number`
- `boolean`
- `null`
- `object`
- `array`

### 2. 无限层级展开

对于嵌套结构：

- `object` 可以进入下一层详情页
- `array` 可以进入下一层详情页
- 下一层中的条目仍可继续进入更深层

这套交互应当支持理论上的无限深度，不把结构深度写死。

### 3. 次页式导航

参考 `Nocturne data-editor` 当前的嵌套编辑方式：

- 主视图展示当前层
- 遇到复杂字段时进入次页
- 次页中继续编辑局部结构
- 保留清晰的返回路径和当前位置感知

### 4. JSON 引用展开

当某个字段表示另一个 JSON 资源引用时：

- 编辑器应允许用户展开被引用 JSON
- 展开后的内容仍使用统一编辑体验
- 展开能力应与普通嵌套结构共用尽可能多的交互和状态模型

当前已确认“需要支持 JSON 引用展开”，但引用协议尚未定稿。

## 三、架构方向

### 通用层

通用层需要至少包含：

- 数据模型层
- 导航与编辑状态层
- 通用 UI 组件层
- 引用解析接口层

## 四、离线能力判断

用户要求该编辑器或插件整体上是离线的，并且不依赖后端服务。

从方向上看，这是可以做到的，但需要注意边界：

- “编辑器核心与 UI” 完全可以纯前端离线运行
- “文件访问” 不能简单假设所有宿主网页都天然拥有本地文件系统权限
- 因此离线能力要拆成两部分：
- 编辑器内核本身不依赖后端
- 文件读写由宿主提供

这意味着第一版更适合定义一套清晰的宿主接口，而不是把文件系统操作直接写死在编辑器内部。

## 五、第一版暂不承诺的能力

- 完整 schema 驱动表单系统
- 所有框架无关的打包形式同时到位
- 复杂远程 URL 引用缓存系统
- Godot `.tres` 直接可视化编辑

## 六、当前待确认事项

### 1. 对外复用形式

待确认是否采用以下之一：

- React 组件优先
- 通用核心 + React 外壳
- Web Component 形式

### 2. 引用协议

待确认是否采用以下之一：

- 纯字符串路径引用
- 显式 `{ "$ref": ... }`
- 两者兼容，但以 `$ref` 为标准

## 七、当前建议

当前最合理的总方向是：

- 先把项目做成“通用编辑器核心 + 可嵌入 UI 层”
- 把文件访问、保存、引用解析下沉到宿主接口
- 让具体项目在仓库外部完成各自接入

这样最符合“先做通用层、本体不掺杂项目业务”的目标。
