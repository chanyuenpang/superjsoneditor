# Super JSON Editor 技术实现文档

## 1. 文档目标

本文档定义 `Super JSON Editor` 的正式技术实现方向。

该项目的定位被严格限定为：

- 一个独立的、通用的 JSON 编辑器项目
- 一个可以被任意网页项目引用的编辑器能力集合
- 一个继承当前 `Nocturne data-editor` 优秀 UI 交互与视觉方案的通用化产物

本文档明确排除以下范围：

- `tiny-world` 专用资产规则
- `Nocturne` 专用数据规则
- 任何单项目宿主逻辑

## 2. 核心目标

### 2.1 通用性

编辑器本体必须对业务语义保持中立。

它应当只理解：

- JSON 值类型
- 嵌套结构
- 路径导航
- 引用展开
- 编辑状态
- 视图状态

它不应理解：

- 某个游戏项目的资产分类
- 某个字段在某项目中的业务含义
- 某个目录在某项目中的特殊工作流

### 2.2 UI 继承

`Super JSON Editor` 不从零重新发明交互。

第一代实现应明确以当前 `Nocturne` 中的 `tools/data-editor` 为母体进行抽离，尽可能保留其优秀部分：

- 主体布局密度
- 表格浏览体验
- 详情面板体验
- 多级嵌套展开方式
- 排版气质
- 视觉层级
- 高信息密度下的可读性

这意味着第一代通用化路线以“抽离复用”为主，而不是“重写一套相似产品”。

### 2.3 离线优先

编辑器本体应当可在无后端服务的条件下运行。

具体含义是：

- 编辑器内核与 UI 不依赖专门的后端 API
- 数据由宿主传入
- 保存由宿主决定
- 引用解析由宿主决定

因此，“离线”是核心能力，“直接文件系统访问”不是本体强绑定能力。

## 3. 技术架构

项目建议拆为两层核心模块。

### 3.1 `core`

`core` 是与 UI 框架解耦的通用逻辑层，负责：

- JSON 文档抽象
- 节点路径模型
- 导航栈模型
- 引用节点模型
- 编辑操作
- dirty 状态计算
- 变更分发
- 视图状态抽象

`core` 不应包含：

- React 组件
- DOM 操作
- 浏览器存储实现
- 宿主文件加载逻辑

### 3.2 `react`

`react` 是默认 UI 实现层，负责：

- 基于 `core` 状态渲染编辑器
- 复用和抽离当前 `data-editor` 的布局与视觉模式
- 提供可嵌入宿主应用的 React 组件入口

`react` 是第一版主交付形态。

虽然未来可以扩展为别的外壳，但第一版不主动追求多 UI 框架同步支持。

## 4. 数据模型

### 4.1 基础值模型

编辑器需要统一支持以下 JSON 值：

- `string`
- `number`
- `boolean`
- `null`
- `object`
- `array`

每个被编辑节点应当具有统一的节点描述信息，例如：

- 当前节点类型
- 当前路径
- 父节点路径
- 展示标题
- 是否可直接编辑
- 是否可进入次页
- 是否是引用节点

### 4.2 路径模型

路径模型应当统一表示嵌套结构位置。

建议路径段只允许两种类型：

- `string`
- `number`

例如：

- `["skills", 0, "effects", 1, "target"]`
- `["root", "children", 2]`

路径模型应成为以下能力的共同基础：

- 值读取
- 值写入
- 节点标题生成
- 面包屑导航
- 引用展开定位
- 校验结果定位

### 4.3 文档会话模型

编辑器在运行时应维护一个文档会话对象。

该对象至少包含：

- 原始根值
- 当前工作副本
- 打开的导航栈
- 已展开引用状态
- dirty 状态
- 选中节点状态
- 宿主上下文

## 5. 嵌套导航模型

### 5.1 次页原则

对于复杂值，不在当前层强行完全展开，而是采用“进入次页”的方式处理。

规则如下：

- primitive 值优先就地编辑
- `object` 支持进入次页
- `array` 支持进入次页
- 次页中的 `object` / `array` 仍然可以继续进入下一层

### 5.2 无限展开

系统不得将层级深度写死为固定层数。

导航状态应使用栈结构表示，例如：

- 第 0 层：根文档
- 第 1 层：`effects`
- 第 2 层：`effects[0]`
- 第 3 层：`effects[0].params`

### 5.3 当前层视图职责

每一层视图只负责当前节点的直接子项展示，不负责把所有后代都平铺在当前层。

这样可以保留当前 `data-editor` 的清晰感，也能避免深层嵌套把主视图压垮。

## 6. 引用展开模型

### 6.1 目标

当 JSON 中某个值表示“引用另一个 JSON”时，编辑器应允许用户展开该引用。

展开后体验应尽量和普通嵌套对象一致，而不是另起一套完全不同的交互。

### 6.2 本体边界

编辑器本体只负责“支持引用节点与引用展开机制”，不负责硬编码具体引用来源。

也就是说，本体不直接决定：

- 如何根据字符串找到文件
- 如何根据 URL 获取内容
- 如何缓存远程数据
- 如何处理宿主权限

这些能力统一通过宿主接口提供。

### 6.3 引用协议

第一版建议将引用协议设计为“可扩展的宿主判定机制”，而不是在本体内硬编码单一协议。

但从长期可维护性看，推荐内部标准优先兼容：

- 显式引用对象，例如 `{ "$ref": "..." }`

同时可以允许宿主扩展识别：

- 字符串路径引用
- URL 引用
- 其他自定义引用结构

### 6.4 引用展开行为

引用展开后建议视为“新的可导航节点”，并保留以下能力：

- 展开来源信息
- 返回原位置
- 区分“当前节点内容”与“引用目标内容”

## 7. 宿主接口

### 7.1 设计原则

由于本体不依赖后端，也不直接假设本地文件系统权限，所以必须定义宿主接口。

宿主接口是 `Super JSON Editor` 可复用性的关键边界。

### 7.2 最小能力集合

第一版宿主接口建议至少包含：

- 加载根文档
- 保存根文档
- 识别某节点是否为引用
- 解析引用目标
- 提供节点标题或显示增强信息

### 7.3 本体与宿主职责分离

本体负责：

- 编辑
- 展示
- 导航
- 状态

宿主负责：

- 数据来源
- 权限
- 存储
- 引用解析
- 项目级约束

## 8. UI 抽离策略

### 8.1 第一代策略

第一代不建议从零重搭 UI。

建议从当前 `Nocturne data-editor` 中抽出以下高价值部分：

- 页面骨架
- 主表视图结构
- 详情页结构
- 嵌套页结构
- 视觉 token
- 常用交互组件

### 8.2 抽离原则

抽离时应遵守以下原则：

- 先保体验，再做抽象
- 先移除业务耦合，再提炼组件接口
- 避免为了“看起来通用”而重写成熟交互

### 8.3 明确允许的变化

虽然总体上保留当前 UI 方向，但以下内容允许在抽离中调整：

- 去除文件列表等与某项目耦合的视图
- 重命名偏业务化组件
- 将具体数据操作重定向到 `core`
- 将宿主相关状态从组件中剥离

## 9. 非目标

第一版明确不追求：

- 完整桌面应用壳
- 所有框架通吃的 UI 实现
- 与任意 schema 标准深度绑定
- 直接编辑非 JSON 数据格式
- 单仓库内同时内置多个项目的专用适配器

## 10. 启动建议

项目正式启动时，建议遵循以下顺序：

1. 先从 `Nocturne data-editor` 中识别可抽离的通用模块
2. 建立 `core` 的最小文档模型与导航模型
3. 搭建 `react` 外壳并迁移当前高质量 UI 结构
4. 将引用展开机制接入宿主接口
5. 再考虑宿主项目如何消费该编辑器

这条路径最符合当前目标：先做纯通用编辑器本体，再由外部项目使用它。
