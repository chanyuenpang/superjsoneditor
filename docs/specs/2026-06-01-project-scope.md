# Super JSON Editor 项目定位与范围

## 目标

Super JSON Editor 要解决两个相关但不同的问题：

1. 提供一个独立的、可复用的通用 JSON 编辑器。
2. 使用这个编辑器，在具体项目中构建专用资产编辑器。

这两个问题必须分层处理。

## 两层架构

### 第一层：通用 JSON 编辑器

这一层是独立项目本身，职责如下：

- 提供可嵌入任意网页项目的 JSON 编辑器能力
- 支持 `object`、`array`、primitive 值编辑
- 支持无限层级展开
- 支持多级次页导航，参考现有 `Nocturne data-editor` 的嵌套展开体验
- 支持 JSON 引用展开
- 优先以“可复用组件/内核”的形式设计，而不是先绑定单一宿主

这一层不应该包含任何 `tiny-world` 业务规则。

### 第二层：项目专用资产编辑器

这一层是宿主项目适配层，职责如下：

- 读取具体项目的资产目录结构
- 定义该项目的引用约定、schema、资源分组和工作流
- 基于通用编辑器拼装出面向该项目的专用编辑器

通用编辑器本体不包含任何具体宿主项目的业务规则。

具体项目如果需要使用本编辑器，应当在各自仓库中完成宿主接入与适配。

## 关键设计原则

### 1. 通用层优先

如果某项能力能在通用层表达，就不要提前写死成任何具体项目规则。

### 2. 前端可嵌入优先

第一版产品形态优先考虑“可被网页项目引用”的编辑器内核，而不是优先做桌面应用。

### 3. 离线可用

编辑器整体需要支持离线使用，但不要求第一版必须依赖独立后端服务。

### 4. 数据模型优先于宿主技术

先定义通用 JSON 编辑模型，再考虑不同项目如何接入，不反过来用某个项目的数据约束通用编辑器。

## 当前明确不做的事

在规格阶段，以下内容不进入本仓库范围：

- 任何 `tiny-world` 专用业务规则
- 任何 `Nocturne` 专用业务规则
- 直接编辑 Godot `.tres` / `.tscn` 等运行时资源格式
- 直接绑定某一种桌面壳技术
- 先做单项目私有工具再回头抽象

## 当前待定问题

- 通用编辑器对外的复用形态是 React 组件、框架无关内核，还是两者同时存在
- JSON 引用的标准协议
- 离线文件访问能力如何在“纯网页可嵌入”前提下落地
- 宿主项目接入时的最小接口集合
