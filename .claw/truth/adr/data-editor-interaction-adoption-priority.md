# ADR：`data-editor` 交互模式的采纳优先级

## Status

accepted

## Context

`super-json-editor` 已经具备字段级脏标记、面包屑、双页/层叠导航和基础保存反馈，但缺少贯穿各编辑器、上下文切换与持久化过程的统一可靠性协议。对 `vendor/data-editor@fe2e3a8ea6422825d6e8fa062e005b53a9d25da5` 的研究表明，其高价值不是某个孤立控件，而是稳定 draft、活跃编辑器 flush、分域 dirty 状态、保存中再次修改的重试以及明确保存状态共同形成的一套编辑可靠性体验。

具体参考事实和代码锚点由 `../data-editor-interaction-patterns.md` 统一拥有，本 ADR 只拥有采纳顺序与取舍。

## Decision

- 第一优先级是建立统一的编辑器可靠性协议：稳定 draft、可注册的活跃编辑器 flush、按持久化域追踪 dirty 状态的保存协调器，以及 `pending`、`saving`、`error`、`blocked-confirmation` 等明确状态。
- 导航、重载、手动保存和其他可能切换上下文的操作，应在该协议之上先 flush 活跃编辑器，再等待保存协调器收束或返回明确阻断。
- 第二阶段加入高频键盘操作与表格选择保护：`Enter` / `Escape` 单元格语义、`Ctrl/Cmd+S`、`/` 聚焦搜索，以及输入控件与范围选择、全局删除之间的隔离。
- 第三阶段再引入渐进式筛选与就地问题反馈：先轻量字段筛选，再按需展开嵌套高级筛选；字段问题贴近字段，配置级问题使用带上下文和动作的 banner。
- 不整体复制 `data-editor` 的 UI 或数据模型；迁移以 `super-json-editor` 现有编辑器结构和持久化边界为所有权基础。

## Alternatives

- 先做快捷键：实施成本较低，但如果没有统一 draft 和 flush 语义，`Enter`、`Escape` 与保存快捷键会继续依赖各编辑器的局部实现，无法解决上下文切换时的可靠性问题。
- 先做高级筛选：用户可见价值高，但复杂筛选不解决输入法中断、丢修改或保存竞争，且会扩大当前状态管理面。
- 按页面零散补丁：短期改动小，但会让提交时机、dirty 状态和离开保护继续分叉，后续难以证明一致性。
- 整体移植参考项目：能快速获得相似外观，却会把参考项目的领域划分和数据模型耦合带入本项目，成本和风险都高于按协议迁移。

## Consequences

- 前期需要先投入不可见的协议与协调器建设，短期功能数量增长会慢于直接添加按钮或快捷键。
- 一旦 flush 和保存状态机成为共享基础，离开保护、快捷键、常驻状态和失败恢复可以复用同一语义，减少光标跳动、组合输入中断和修改丢失风险。
- 后续交互必须明确属于编辑器 draft、文档内容、项目配置、个人配置或共享配置中的哪个持久化域；不能再用单一布尔 dirty 覆盖所有情况。
- 每个阶段都应以 `../data-editor-interaction-patterns.md` 的边界检查为约束，但参考提交变化时必须重新做实现锚点的新鲜度检查。
